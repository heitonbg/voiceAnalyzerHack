# Эксперимент: один вызов sherpa-onnx на всю запись

Дата: 2026-11-07. Android Emulator API 36, x86_64, RAM 4096 MB. Эталон пользователя «Подорожник»: 1 313 024 ms, 127 размеченных начал, четыре участника. Инференс выполнен внутри Android. Ранее сохранённые ASR-слова повторно использованы без запуска GigaAM. Эталонные ID применялись только для оценки.

## Архитектура

Стабильный `BoundedDiarization` передаёт в `OfflineSpeakerDiarization.process()` каждый 30-секундный блок отдельно (с контекстом до 1 s), затем вычисляет embeddings отдельных дорожек и назначает глобальные ID сам. В эксперименте PCM16 mono 16 kHz прочитан в один FloatArray: 21 008 384 отсчёта, 84 033 536 bytes. Для каждого варианта создан один diarizer с Pyannote segmentation 3.0 и TitaNet Small; `process(samples)` вызван один раз. Автоматический режим использовал `numClusters=-1, threshold=0.5`; фиксированный — `numClusters=4`. Это существующий sherpa-onnx 2.0.1 AAR; вызов проверен компиляцией и реальным Android-тестом.

Native-сегменты преобразованы в интервалы 16 kHz без сброса временного смещения. Пересечения отмечаются только на части интервала, где одновременно активны разные ID; первый тест ошибочно помечал весь сегмент overlap даже при коротком пересечении, поэтому его оценки качества отброшены. Исправленные варианты A/B/C ниже используют один и тот же сохранённый ASR и `WordSpeakerPlanner` / `UtteranceMerger`.

Сэмплирование памяти — 200 ms, не гарантированный абсолютный пик. ASR-модель не загружалась при B/C; вместе с ней память и полное время не измерены. Android-тесты B и C завершились `OK (1 test)` без OOM. A — ранее измеренный свежий production-проход, B/C — последовательные diarization-only проходы, поэтому показатели времени нельзя прямо трактовать как честный end-to-end RTF B/C.

Матрицы ошибок по четырём эталонным говорящим включены в агрегаты [auto](results/whole-file-diarization-auto.json) и [K=4](results/whole-file-diarization-k4.json). У четвёртого участника в C только четыре эталонных начала: два попали в unknown, два в разные чужие ID; улучшения по нему нет. В B 85 native ID при четырёх эталонных участниках — сильная перекластеризация. В C speaker_2 и speaker_3 смешиваются: оба часто отнесены к двум одним и тем же предсказанным ID. Из 166 native-интервалов K=4 два основных ID содержат 541 434 и 736 155 ms речи, а два остальных — всего 1 333 и 641 ms. Так что сам переход от независимых 30-секундных вызовов к одному вызову не решил основную проблему качества голосовых кластеров.

Здесь использована старая coarse-метрика: сначала строка, содержащая эталонную секунду, иначе ближайшее начало в пределах 5 s; ID сопоставляются оптимальной перестановкой. Она чувствительна к неточным эталонным секундам и длинным репликам. Для B/C отдельно посчитан строгий вариант по ближайшему началу: B 12/120, C 52/115; baseline по такому правилу пока не пересчитан, поэтому строгие показатели нельзя сопоставлять с A. RTTM с точными интервалами отсутствует: DER/JER недоступны. Независимой эталонной записи для A/B/C нет.

## Решение

Оставить v25 в production. Автоматический полный вызов резко ухудшает speaker ID и требует больше памяти. Фиксированный K=4 даёт лишь +1 попадание на одном файле и отдельный native-проход 183.9 s; выигрыш по скорости и устойчивости не подтверждён. Экспериментальный код живёт только в opt-in `ReferenceEvaluationTest`, не меняет экспорт, UI и модели APK. Сырые native-интервалы сохранены в app external files на эмуляторе как `whole-file-native--1.json` и `whole-file-native-4.json` для последующего анализа без ASR.

Запуск: `ReferenceEvaluationTest` с `evaluateReference=true`, `freshReference=false`, `wholeFileExperiment=true` и `wholeFileAutoOnly=true` либо `wholeFileFixedOnly=true`. Требуются локальные импортированная запись, reference.txt и ASR checkpoint. Полные команды — в [testing.md](testing.md).
